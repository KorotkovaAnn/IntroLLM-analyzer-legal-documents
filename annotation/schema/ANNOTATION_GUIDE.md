# Инструкция по разметке договоров (схема 0.2)

Образцы со всеми четырьмя слоями: [контракт по 44-ФЗ с этапами](../gold/44fz_0001.gold.json) и
[проект договора по 223-ФЗ](../gold/223fz_0001.gold.json), в котором часть полей оставлена пустой.

## Порядок работы с одним договором

Команды ниже запускаются из папки `annotation`. Замените `DOC_ID` на идентификатор договора.

1. Получить канонический текст: DOCX → `pandoc -t plain --wrap=none файл.docx -o text/DOC_ID.txt`
   (старый .doc сначала сконвертировать в DOCX через LibreOffice). Если таблица выпала (`[TABLE]`),
   вставить её текст вручную. После этого текст больше не менять.
2. Нарезать на пункты: `python tools/segment.py text/DOC_ID.txt clauses.json v` и просмотреть список.
   Исправить ошибки нарезки (склеенные или разорванные пункты), если они есть.
3. Заполнить слой 2 (поля) по образцу.
4. Проверить три риска и заполнить слой 3 (`layer3_risks`) по [инструкции по рискам](RISK_ANNOTATION_GUIDE.md).
5. Заполнить слой 4 (вопросы) по образцу.
6. Запустить `python tools/validate.py gold/DOC_ID.gold.json` и убедиться, что получен статус `OK`.
   Валидатор проверяет схему, ссылки на пункты, цитаты и поля вопросов. Сопоставление условий с нормами выполняет разметчик.

## Единицы слоя 1 (пункты)

- `preamble` — шапка (название, номер, ИКЗ, город, дата) и преамбула.
- Нумерованные пункты `1.1`, `7.3.2` и т.д. Ненумерованные абзацы, подпункты «а)», «1)», «-» входят в пункт выше.
- Раздел без нумерованных пунктов (обычно реквизиты) — единица с номером раздела: `14`, `17`.
- Приложения — `app1`, `app2`, … целиком.

## Главные правила слоя 2 (поля)

1. **Поля не удаляются никогда.** Нет значения в договоре — `null` и пояснение в `note`.
2. **Необязательные блоки** (`optional.advance`, `security`, `warranty`; `subject.items`, `subject.stages`,
   `price.stage_prices`, `terms.execution.schedule`) — `null`, если в договоре их нет.
3. **Пустое поле проекта** («___») — `null`, в `note` пишем «проект: не заполнено», цитату даём на пустое место.
4. **Значения из списков** — только из перечня в схеме:
   - `price.vat`: включён / сверху / без НДС / не указано / вариативно (вариант выбирается при заключении);
   - `price.kind`: твёрдая / максимальная / формула / по заявкам / не указано;
   - `role_norm`, `payer`: заказчик / исполнитель (поставщик, исполнитель, подрядчик → «исполнитель»).
5. **Даты** — в формате ГГГГ-ММ-ДД в поле `date`; относительные сроки («30 календарных дней с даты заключения») — в поле `relative`.
6. **Числа** — числом, без пробелов: `167366.40`.
7. **Неустойки** — каждая отдельным элементом списка: кто платит, за что, пени или штраф, размер.
   Если по шкале применима одна ставка (например, «цена до 3 млн → 10%»), пишем применимую и это поясняем.
8. **Неприменимые пункты** (относятся к другой процедуре или виду договора) — в `liability.not_applicable` с причиной.
9. **Цитата** — короткий дословный фрагмент (обычно 5–25 слов), однозначно подтверждающий значение.
   Неразрывные пробелы, мягкие переносы и ё/е при проверке нормализуются.

## Правила слоя 3 (риски)

- Заполняем все три проверки в `layer3_risks.checks`: односторонний отказ, автопролонгация, несимметричная неустойка.
- Для каждой проверки записываем итог, наличие условия, объяснение с позиции поставщика, пункты с дословными цитатами и `norm_refs` из базы норм.
- Сверяем применимость по закону, виду договора и редакции нормы. Недостающие сведения о закупке указываем в `legal_context_note`, оговорки по конкретной проверке — в `legal_note`.
- Определения рисков, значения полей, перечень норм и результаты по обоим образцам собраны в [инструкции по слою рисков](RISK_ANNOTATION_GUIDE.md).

## Правила слоя 4 (вопросы)

- 8–10 вопросов на договор. Типы: прямой, условный, составной, расчётный, наличие.
- Минимум 2 вопроса без ответа (`answerable: false`, `clauses: []`, `quote: null`).
  Если рядом есть связанный пункт — указать его в `related_clauses`.
- Вопрос о незаполненном в проекте поле — тоже `answerable: false` (см. 223fz_0001, q09).
- Формулировки — как спросил бы поставщик, а не юридическим языком.

## Раздел notes

Записываем всё необычное: опечатки и ошибки ссылок в оригинале, нестандартное оформление,
сложности для парсера и общие наблюдения по документу. Оговорки, влияющие на конкретный риск, записываем в его `legal_note`.
